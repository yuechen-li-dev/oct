# OCTGEN-M0: Interpreted Oct as Optional Compile-Time Language for Go

> **Experimental, post-1.0 work.** OctGen is not an Oct 1.0 language feature,
> stable CLI command, compiler phase, or compatibility promise.

## Thesis and result

OCTGEN-M0 tests external staged generation: ordinary, type-checked interpreted
Oct selects a small declaration model, and a Go host renders ordinary committed
Go source. `go build` and downstream consumers never execute OctGen or require
Oct. The M0 specimen supports the thesis for a narrow, realistic value-dispatch
family: readable Oct replaces five concrete wrapper dispatch declarations while
the generated Go remains concrete, formatted, and directly debuggable.

This is deliberately not Go compiler integration. `go generate` is an explicit
maintenance action; `go build` and `go test` consume the resulting `.go` file.

## Selected specimen

[`cmd/octxiliary-time/main.go`](../../cmd/octxiliary-time/main.go) had one
handwritten `dispatch` switch with five concrete Time wrapper names:

- `TimeNowIso8601`;
- `TimeParseIso8601`;
- `TimeFormatIso8601`;
- `TimeUnixSecondsNow`;
- `TimeFormatUnixSecond`.

Each name has a closed operation mode and a declared Octxiliary argument-kind
vector. The common rule is: validate kinds, dispatch an established Time API
operation, and return a typed Octxiliary value. Go type parameters can abstract
the validation helper but cannot define a value-driven exhaustive `switch` or
materialize concrete operation declarations from the descriptor data. The
specimen is production sidecar code, has no generator bootstrap dependency, and
is behaviorally covered by ordinary Go tests.

The source model is
[`time_dispatch.oct`](../../cmd/octxiliary-time/time_dispatch.oct). It uses
ordinary records, a tag-only enum, arrays, an explicit `for` loop, and an `if`;
it adds no macro, quasiquotation, reflection, or compile-time-only Oct syntax.

## Architecture

```text
time_dispatch.oct
  -> project.Load (normal Oct parser/package loader)
  -> typecheck.CheckProgram (normal type checker)
  -> interpret.CallFunctionWithArgsAndOptions(..., "Generate", ...)
  -> bounded GeneratedTimeDispatch runtime record
  -> internal/octgen validation and go/ast construction
  -> go/format
  -> host-controlled atomic replacement of time_dispatch.generated.go
```

The only host/interpreter seam is the existing exported `interpret.Value` return
from `CallFunctionWithArgsAndOptions`. M0 decodes only one record shape:
`GeneratedTimeDispatch { Package: String Operations: TimeOperation[] }`.
`TimeMode` is a closed, host-owned four-mode vocabulary. The host rejects bad
record shapes, unsupported kinds/modes, duplicate names, wrong mode arity, and
models with fewer than three operations. It builds Go AST nodes directly; no
unbounded Go source strings or template language form the generation protocol.

Every result begins with `// Code generated by OctGen. DO NOT EDIT.` and is
rendered by `go/format`.

## Workflow

From the repository root:

```powershell
go run ./tools/octgen generate -input cmd/octxiliary-time/time_dispatch.oct -output cmd/octxiliary-time/time_dispatch.generated.go
go run ./tools/octgen check -input cmd/octxiliary-time/time_dispatch.oct -output cmd/octxiliary-time/time_dispatch.generated.go
go generate ./cmd/octxiliary-time
go test ./cmd/octxiliary-time
```

`cmd/octxiliary-time/main.go` contains the equivalent explicit directive:

```go
//go:generate go run ../../tools/octgen generate -input time_dispatch.oct -output time_dispatch.generated.go
```

`check` regenerates in memory and fails without modifying the committed file
when it is missing or byte-stale.

## Bootstrap, capabilities, and determinism

`tools/octgen` is ordinary Go code that imports the existing Oct parser,
typechecker, and interpreter packages. It does not invoke a prebuilt `oct`
binary and its own build does not depend on any OctGen output. The selected
sidecar also does not participate in building OctGen, so no bootstrap cycle is
introduced.

For M0 the Oct generator has no filesystem, environment, clock, random, or
network capability. The normal package loader reads the generator source and
its declared imports (the specimen has none). The host alone writes one output
path supplied on the command line. That path must be a `.go` file inside the
generator's directory; path traversal and sibling/parent outputs are rejected.
The model has no output-path field, so it cannot declare an additional output.
Writes use a temporary file followed by replacement only after interpretation,
model validation, AST construction, and formatting all succeed.

The model contains only ordered arrays and closed values. Repeated generation
is tested byte-for-byte, and the committed result contains no source-machine
paths, timestamps, random values, or ambient environment data.

## M0 measurements

| Measure | Result |
| --- | --- |
| Concrete dispatch declarations generated | 5 |
| Host behavior modes | 4 |
| Handwritten dispatch lines removed | 37 |
| Oct generator lines added | 35 |
| Generated Go lines | 52 |
| OctGen host/tool production infrastructure lines added | 389 |
| Duplicated operation name/kind/mode information eliminated | five handwritten switch cases become one ordered Oct descriptor array |
| Regeneration time | 193 ms for `go run ./tools/octgen generate ...` on this checkout |
| Determinism | byte-for-byte on repeated generation |

The infrastructure-to-specimen ratio is intentionally high for a first seam.
M0 demonstrates architecture and maintenance boundaries; it does not claim
that a five-entry switch alone amortizes the tool for all repository code.

## Ergonomics observations

| Observation | Classification | Evidence / disposition |
| --- | --- | --- |
| Explicit `var operations = [declared[0]]` plus `for`/`Append` is needed to transform a known array without a general map helper. | collection transformation friction | Consider a library helper only after an ordinary Oct and Oct Make use case needs the same shape. |
| Every descriptor record repeats field labels. | record construction/update friction | Small and readable here; not evidence for a language change. |
| The host needs detailed record decoding and provenance messages. | generator API problem | Keep the narrow model and improve reusable host helpers only after a second declaration family. |
| Returning an exported `interpret.Value` required no interpreter alteration. | interpreter embedding friction | No current friction beyond model-specific decoding. |
| Closed Time operation modes are host-owned behavior. | not a language limitation | A broader model should add structured declarations only when a second specimen demands them. |

There is no evidence here for Oct macros, quasiquotation, reflection, or heavy
generics. The collection observation is also relevant to Oct Make: a pure,
typed collection-transform helper could improve plan construction and ordinary
Oct without making generation special.

## Limitations and next recommendation

M0 supports one `dispatch` declaration vocabulary and four host-known time
operation bodies. It does not bind the full Go AST, parse arbitrary Go strings,
support imports selected by Oct, or enable `go build` to run Oct. It also does
not demonstrate a value- or schema-specialized implementation family yet.

The recommendation is **OCTGEN-M1 production dogfood**: select one additional
production registry/descriptor family, retain the same external staging and
capability boundary, and only broaden the structured declaration vocabulary if
that second specimen requires it.
